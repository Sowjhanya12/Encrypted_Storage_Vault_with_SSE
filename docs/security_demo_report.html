D1

The cloud never receives plaintext content, filenames, keywords, or vault keys

confirmed secure

A document containing the words 'zephyrion', 'classified' and 'budget', uploaded under a deliberately identifiable filename, was uploaded and then searched for. Every HTTP request the trusted client sent to the cloud during that workflow, and the cloud's own on-disk database afterwards, were scanned byte-for-byte for the plaintext words/filename and for the actual derived K_file/K_index key bytes -- none were found anywhere.

Audit reference: architecture.html §02 trust boundary; Opus audit Probes P2, P12

Cloud can see
Opaque AES-GCM blobs (nonce/ciphertext/tag) for the document and its filename; opaque hex labels and opaque encrypted values in sse_index; a document's byte size and upload timestamp.
Trusted client can see
The real filename ('quarterly_salaries_confidential.txt') and full plaintext content.
Remains secret
The plaintext content and filename; the search keyword; K_file; K_index; the Argon2id master key; the vault password -- confirmed absent from every captured request/response and from the raw cloud database file.

D2

Repeated searches for the same keyword are recognisable to the cloud

confirmed leakage (by design)

Searching 'financial' twice sent the byte-identical K1 token to the cloud both times; searching the unrelated keyword 'gardening' sent a different token. F(K1, counter) is deterministic by construction (HMAC-SHA256), which is what makes search work at all -- and exactly what makes repeat queries linkable.

Audit reference: architecture.html §01/§10 (accepted SSE cost); crypto.py's prf() docstring

Cloud can see
That the exact same search happened twice (identical K1 bytes), and that a third search was for something different (a different K1) -- without ever learning what keyword either one was.
Trusted client can see
The real keywords behind each token ('financial', 'gardening').
Remains secret
Which plaintext keyword a given K1 corresponds to (HMAC is one-way).
Intentional limitation
Determinism is inherent to any *searchable* symmetric encryption trapdoor, not a bug in this implementation -- hiding it requires a fundamentally different (randomised-token / ORAM-backed) construction, out of scope per §01.

D3a

The cloud observes exact result counts and total index size (setup-size leakage)

confirmed leakage (by design)

Three searches against the SAME live vault returned cloud-visible match counts of 3, 1 and 0 respectively -- the cloud's own /search response includes 'count' explicitly, and it can also read the total row count of sse_index directly (a bare SQL COUNT(*), no decryption needed) to learn how many (keyword, document) postings the whole vault contains.

Audit reference: architecture.html §09 (setup-size leakage)

Cloud can see
Exact match count per search ([3, 1, 0]); total index size (12 rows) at any time.
Trusted client can see
The same counts, plus the real keywords and filenames behind them.
Remains secret
Which keyword or document identity a given count/row corresponds to.
Intentional limitation
Result-count and setup-size leakage are fundamental to this class of SSE (§01/§10 scope) -- suppressing them needs padding/ORAM-style constructions this project does not implement.

D3b

The cloud observes the real HTTP access pattern: which opaque document IDs are fetched right after a search

confirmed leakage (by design)

Captured via wire_log against the real live cloud process (not simulated): searching 'budget' produces the literal HTTP sequence POST /search -> GET /documents/<id> for each of the two documents that share that keyword, with nothing else interleaved. Repeating the identical search reproduces the identical two-document access pattern; a different keyword ('solo') produces a different, disjoint single-document pattern. The cloud never decrypts anything, but it directly observes which opaque document records get 'touched' as a consequence of which search, and can tell two searches were for the same underlying keyword from that pattern alone.

Audit reference: Opus audit M4 (search eagerly fetches every match, amplifying access-pattern leakage)

Cloud can see
The exact request sequence for each search (1 POST /search + N GET /documents/<id>, N = the match count); the opaque doc_id of every document a search's results caused to be fetched; that a repeated search reproduces byte-identical access pattern; that a different keyword produces a distinguishable access pattern -- all without ever learning a real keyword or filename.
Trusted client can see
The real keyword ('budget'/'solo') and filenames behind every fetched doc_id.
Remains secret
Which plaintext keyword or filename any given opaque doc_id corresponds to.
Intentional limitation
Per audit finding M4: api_search() eagerly fetches every matching document's encrypted name to resolve filenames for the browser response, which is what turns a single opaque search into an observable multi-request access pattern. A production system wanting to suppress this would cache decrypted filenames client-side (Opus fix-order item 5) instead of re-fetching on every search -- out of scope for this fix, which only had to DEMONSTRATE the leakage, not eliminate it.

D6

Wrong-password unlock fails closed; the destructive-rebuild attack path is unreachable

mitigated (security fix verified)

Reproduced the exact Probe P1 sequence (correct unlock, upload, lock, wrong-password unlock, upload attempt) while capturing every HTTP call the client made to the cloud. Zero of the 2 calls made during the attack sequence were a POST /documents or POST /index/replace -- the cloud never received either, because unlock itself refused first.

Audit reference: Opus audit H1, Probe P1; fixed in phase6_h1_h2_fix (unlock verifier + all-or-nothing rebuild)

Cloud can see
The failed unlock attempt itself (a GET on its own meta rows) -- nothing more.
Trusted client can see

D7

The static index is rebuilt from the whole corpus on every single upload

confirmed leakage (by design)

Three uploads in sequence triggered [1, 2, 3] document re-fetches respectively -- upload N re-fetches and re-decrypts all N documents that exist by then, observable purely from HTTP call volume, confirming the O(n)-per-upload cost the code's own docstrings claim.

Audit reference: architecture.html §10 'static-only assumption'; indexer.py/_rebuild_and_push_index() docstrings

Cloud can see
The number of GET /documents/<id> calls per upload growing linearly -- i.e. it can infer, from traffic volume alone, that a full-corpus operation runs on every write, which is itself a form of operation-pattern leakage beyond content.
Trusted client can see
The same, plus that this is simply how the design works.
Remains secret
Which specific documents were re-fetched stays opaque (random doc_ids).
Intentional limitation
Explicitly named and accepted in §10: no incremental index update, no forward privacy -- a real incremental/forward-private SSE construction is out of scope for this project.

D8

A search token captured once remains valid forever, and silently grows to cover future data

confirmed leakage (by design)

K1 for 'zephyrion' was captured from a live search while only ONE matching document existed. A second matching document was then uploaded, triggering a full index rebuild the captured token played no part in. Replaying the OLD token directly against the live cloud -- with no involvement from the trusted client at all -- now returns BOTH documents.

Audit reference: Opus audit M5 (confirmed); architecture.html §10 (no forward privacy claimed)

Cloud can see
Nothing new is required of the cloud here: it is the same deterministic F(K_index, keyword) it always sees (D2) -- the point is that possessing one old token is permanently as good as possessing a live one, for that keyword, forever.
Trusted client can see
That this is how the static construction behaves -- no client action needed.
Remains secret
Which keyword the token corresponds to, in isolation.
Intentional limitation
This is exactly M5's finding and architecture.html §10's explicitly out-of-scope forward privacy -- a forward-private SSE construction (e.g. rotating K1 per epoch) would close this, and is named future work, not attempted here.

D9

A conjunctive (AND) search is two ordinary single-keyword searches back-to-back, intersected only by the client -- but their co-occurrence is still cloud-visible

confirmed leakage (by design)

Searching 'quarterly financial' (an implicit AND) produced exactly two calls to the cloud's unmodified /search route, each carrying a single k1 token -- byte-identical in shape to D2's ordinary single-keyword search. The cloud was never asked to compute an intersection and never received both tokens in one request; client_app.py intersected the two decrypted doc_id sets itself, after both cloud round trips had already completed.

Audit reference: architecture.html §01 (scope reversal, documented) and §09 (query-conjunction row); client/search.py module docstring

Cloud can see
Two independent search requests, each with its own token and its own result count/access pattern (identical leakage to a lone single-keyword search, per D2/D3) -- PLUS that these two arrived together, in this order, with no unrelated traffic between them, which a request-timing/log analysis can read as 'these two keywords were queried jointly' even though no field in either request says so.
Trusted client can see
The real keywords ('quarterly', 'financial') and that a document matched both.
Remains secret
The plaintext keywords themselves, and which specific document matched (only its opaque doc_id and access pattern are cloud-visible, per D3).
Intentional limitation
This co-occurrence signal is the scoped cost of choosing the simplest correct construction (client-side intersection of independent searches) over a cross-tag scheme (e.g. OXT) that could hide more -- see client/search.py's module docstring for that design decision. Suppressing it entirely needs a real multi-keyword protocol, out of scope per the same depth-over-breadth call §01 already makes for the base scheme.
